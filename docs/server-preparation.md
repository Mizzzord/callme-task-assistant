# Подготовка CallMe к переносу на сервер

Этот комплект содержит исходный код и шаблон настроек. Он предназначен для подготовки и локальной проверки; сам по себе он не публикует приложение и не переносит пользовательские данные. Перед открытием доступа извне нужно выбрать схему входа и проверить защиту и конфигурацию на конкретном сервере.

Регистрация по имени и паролю предлагается при открытии, но окно можно закрыть: гостевой доступ к API остаётся доступен. Это не ограничение публичного доступа к серверу. До публикации нужно отдельно определить и обеспечить защиту входа и гостевого режима.

## Что потребуется

- Сервер с Node.js 24.20 или совместимой версией Node.js 24, npm и постоянным диском. Приложение использует встроенный `node:sqlite` и запускается одним процессом.
- Домен с HTTPS и обратный прокси. Микрофон в браузере требует защищённого контекста; HTTP на внешнем адресе для него не подходит.
- Доступные только владельцу приложения файлы конфигурации и данных. Не помещайте `.env`, базу, ключ шифрования Яндекса и резервные копии в общедоступные каталоги и Git.

## Проверка исходного комплекта

В распакованном каталоге выполните:

```sh
npm ci
npm test
npm run build
HOST=127.0.0.1 PORT=3001 npm start
```

На сервере приложение следует слушать только на loopback, а HTTPS завершать на обратном прокси. Для постоянного запуска используйте менеджер процессов системы от отдельного непривилегированного пользователя, с рабочим каталогом приложения, автоперезапуском и доступом на запись только к каталогу данных. Прокси должен передавать `/api` и остальные пути приложению; запросы с аудио и вложениями могут достигать 10 МБ. Настройте ограничения запросов и размер тела запроса с учётом этих размеров.

Для Ubuntu приложен пример `deploy/callme.service`. Перед применением проверьте путь Node.js, создайте системного пользователя `callme`, каталог приложения `/opt/callme`, доступный ему каталог данных `/var/lib/callme` и защищённый конфигурационный файл `/etc/callme/callme.env`. Установите зависимости и соберите проект в `/opt/callme`; шаблон использует `tsx`, который находится в devDependencies, поэтому при установке нельзя исключать devDependencies. Не копируйте и не запускайте unit до проверки фактической конфигурации сервера. Эта конфигурация не устанавливает TLS и не публикует сервис.

DNS-имя `callme.s2k.studio` при локальной проверке указывало на `178.253.38.41`. Для него подготовлен пример `deploy/nginx-callme.conf`; до его применения нужно выпустить сертификат, проверить занятость портов и действующую конфигурацию Nginx, проверить `nginx -t` и продумать обновление сертификата. Конфигурация не устанавливает Nginx или сертификат и не применялась на сервере. Не включайте журналирование параметров callback: они содержат код авторизации.

Существующий ограничитель попыток входа работает в памяти и использует адрес подключившегося клиента. При работе за прокси приложение видит адрес прокси, если отдельно не настроена доверенная цепочка прокси; поэтому ограничение на уровне прокси нужно проверять для реальных клиентских IP. Не доверяйте произвольному `X-Forwarded-For` из интернета. Ограничитель сбрасывается при перезапуске и не является распределённым.

## Настройки

Создайте конфигурацию на сервере из `.env.example` и задайте `COOKIE_SECURE=true` при работе через HTTPS. Не включайте платные API без настройки согласованного бюджета и оценок стоимости. Согласованный лимит составляет 500 ₽ за 30 дней; локальный резерв не является счётом Яндекса. Перенесите учёт расходов вместе с базой и проверьте, что отдельные экземпляры не позволяют превысить общий лимит. Перенос локальной конфигурации и ключей выполняйте отдельно по защищённому каналу; архив с исходным кодом их не содержит.

Сейчас резерв в базе суммируется за всё время и автоматически через 30 дней не обновляется. Это не контроль фактического счёта и не общий ограничитель для нескольких копий приложения.

Для сервера задайте `YANDEX_REDIRECT_URI=https://callme.s2k.studio/api/yandex/callback` и зарегистрируйте этот адрес в каждом используемом OAuth-приложении Яндекса. Локальный режим без этой переменной сохраняет callback `http://127.0.0.1:8765/api/yandex/callback`. Точные правила совпадения адреса описаны в [документации Яндекс ID](https://yandex.ru/dev/id/doc/ru/register-auth). После запуска необходимо проверить реальную авторизацию на домене; наличие настройки и локальные тесты с имитацией Яндекса этого не подтверждают.

## Перенос и восстановление данных

В архиве только исходный `data/events.csv`: он не содержит текущих задач и аккаунтов. При первом запуске с пустой базой пользовательские данные не появятся автоматически. Для новых пустых пространств установите `CALLME_SEED=false` в серверном конфигурационном файле: иначе при создании пространства импортируются демонстрационные задачи. Изменение настройки не удаляет уже импортированные записи.

Текущие задачи, аккаунты, сессии, переписка, вложения, подключения и резерв расходов находятся в SQLite. Для переноса используйте согласованный SQLite backup или остановите исходный сервер и скопируйте согласованную базу с её WAL-файлами. Ключ `data/.yandex-vault/key` необходим для расшифровки уже сохранённых подключений Яндекса. Храните резервные копии базы и ключа отдельно и защищённо; потеря ключа потребует переподключения сервисов. Не запускайте два независимых сервера на одной копии базы в ожидании автоматической синхронизации изменений.

Перед переключением пользователей проверьте восстановление копии, вход, права команды, задачи, вложения, работу HTTPS и реальный OAuth callback. Переход на сервер и перенос действительных данных выполняются только после согласования конкретного сервера и способа переноса.
